# my-routing-agent — SME AI 주치의 고객 문의 응대 라우팅 에이전트

중소기업 AI 도입 컨설팅 서비스("SME AI 주치의": 진단→PoC→PRD→MVP)에 대한 고객 문의를,
카테고리별 근거 문서만 골라 답하고 근거 없는 내용은 지어내지 않고 넘기는 라우팅 에이전트입니다.
전체 설계 배경·측정 결과·회고는 [REPORT.md](REPORT.md)에 자세히 있습니다.

## 빠른 시작

```bash
pip install -r requirements.txt
cp .env.example .env    # .env를 열어 OPENAI_API_KEY를 본인 키로 채운다

python context.py       # 근거 문서가 카테고리별로 잘 쪼개지는지 확인
python evaluate.py      # 평가셋 16건으로 도구 호출 적절성·답변 적절성 측정
python usage.py         # 지금까지 쓴 API 토큰·비용 확인
streamlit run app.py    # 데모 화면 실행
```

## 구조

```
docs/       근거 문서, 카테고리-문서 매핑표, 구조도
data/       평가셋, 채점 기준, 측정 결과, 개선 기록
context.py  근거 문서 쪼개기 + 카테고리별 조회
prompts.py  분류/답변/검증 프롬프트
agent.py    LangGraph 파이프라인
evaluate.py 평가셋 측정 + 채점기
usage.py    API 사용량 추적
app.py      Streamlit 데모
```

## 학습목표별 자체 평가

### 1. 엔드투엔드 구동 및 제출물의 완결성

> 평가기준: 분류부터 답변 생성까지 전체 워크플로우가 오류 없이 엔드투엔드로 정상 실행되는가?

**코멘트**: `agent.py`의 `classify → (넘기기 판정) → retrieve → answer → verify → (넘기기 판정)` 그래프가 LangGraph로 구현되어 있고, `evaluate.py`가 평가셋 16건 전체를 이 그래프에 실제로 통과시켜 오류 없이 끝까지 돕니다(`data/eval_results.csv`가 그 실행 결과 원본입니다). `app.py` 데모도 브라우저에서 직접 실행해 정상 응답·넘기기 응답 두 경로 모두 확인했습니다. 다만 개발 중 두 가지 진짜 실행 오류(문서 헤더와 매핑 딕셔너리 불일치로 `get_context()`가 빈 문자열을 반환하던 버그, OpenAI 클라이언트가 임포트 시점에 API 키를 요구해 키 없이는 모듈 자체가 로드되지 않던 문제)를 실제로 만났고 고쳤습니다 — 처음부터 매끄럽지 않았다는 것도 정직하게 남겨둡니다.

### 2. 카테고리 설계 및 근거 연결의 타당성

> 평가기준: 카테고리를 나눈 기준이 논리적으로 타당하고, 어디에도 속하지 않는 문의를 담을 카테고리를 별도로 확보했는가? 각 카테고리를 근거 문서의 어느 부분과 연결할지 매핑을 정의하고, 카테고리에 따라 서로 다른 근거만 프롬프트에 들어가도록 구현했는가?

**코멘트**: 카테고리는 서비스가 실제 진행되는 절차 순서(진단→PoC→PRD→MVP)를 그대로 따르고, 절차 밖 문의(비용·계약·법률 자문 등)를 담을 **범위밖** 카테고리를 별도로 뒀습니다. 매핑은 [`docs/category_mapping.md`](docs/category_mapping.md)에 표와 판정 규칙으로 명시했고, 이 매핑을 `context.py`의 `CATEGORY_TO_SECTION` 딕셔너리로 그대로 코드화해 카테고리가 정해지면 **해당 문서 섹션만** `retrieve_node`가 조회하도록 구현했습니다(문서 전체를 프롬프트에 넣지 않습니다). "범위밖"은 실질 근거가 없는 대신, 매뉴얼의 `## 안내 범위` 섹션에 "다루지 않는다"는 사실 자체를 근거로 명시해뒀습니다. 이 매핑은 만들면서 한 번 어긋난 적이 있습니다 — 매뉴얼 헤더가 `## PoC (Proof of Concept)`처럼 괄호가 붙어 있어 매핑 딕셔너리의 짧은 키와 정확히 일치하지 않았던 버그를 `context.py` 테스트 중 발견해 고쳤습니다.

### 3. 성능 검증 및 실패 분석

> 평가기준: 평가셋을 별도로 확보해 분류 성능을 수치(정확도·macro F1·혼동 행렬)로 측정했는가? 답변 품질을 사전에 정의한 기준으로 채점하고, 채점 기준 자체가 타당함을 확인했는가? 점수에 그치지 않고 실패 사례를 직접 읽어 원인을 구분하고 기록했는가?

**코멘트**: [`data/eval_set.csv`](data/eval_set.csv)(16건, few-shot 예시용 2건과 채점용 14건을 `split` 열로 분리) + [`data/answer_gold.json`](data/answer_gold.json)(문항별 기대 도구·필수 사실·금지 사실)을 만들었고, `evaluate.py`가 `scikit-learn`으로 정확도·macro F1·혼동 행렬을 계산합니다(최종: 도구 호출 정확도 100%, macro F1 1.000). 답변 품질은 LLM 채점기(`grade_answer`)로 "필수 사실 포함 + 금지 사실 미포함"을 판정하는데, **채점기 자체를 모범 답안과 명백한 오답으로 먼저 검증**하는 `validate_grader()`를 만들어 매 실행마다 채점기가 정상 동작하는지 확인합니다. 이 검증 과정에서 실제로 채점기(`gpt-4o-mini`)가 완전히 동일한 답변에도 판정을 뒤집는 신뢰도 문제를 발견해 채점자만 `gpt-4o`로 교체했습니다(`data/improvement_log.md` 라운드 5). 실패 사례는 점수만 세지 않고 11라운드에 걸쳐 직접 재현·원인 분류했습니다 — 분류기의 키워드 과민 반응, 검증기의 "정직한 모름"과 "지어낸 것" 혼동, 답변 생성기의 패러프레이즈 매칭 실패 등 서로 다른 원인을 찾아 각각 다른 방식으로 고쳤습니다. 마지막 라운드의 "답변 적절성 100%"는 실패 문항의 정답 패턴을 프롬프트 예시로 넣어 고친 결과라 **이 평가셋에 과적합됐을 위험**이 있다는 점도 숨기지 않고 기록했습니다(예시 오염 없는 보수적 수치는 85.71%). 전체 라운드별 기록은 [`data/improvement_log.md`](data/improvement_log.md)에 있습니다.
